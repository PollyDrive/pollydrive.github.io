Ключевые инженерные особенности фазы поглощения

При подготовке к проектированию или созданию системы поглощения данных сле­

дует обратить внимание на некоторые основные моменты и вопросы, связанные

с этим процессом.

♦ Каков сценарий использования поглощаемых данных?

♦ Можно ли повторно использовать эти данные и избежать поглощения несколь-

ких версий одного и того же набора данных?

♦ Куда направляются данные? Каково место назначения?

♦ Как часто должны обновляться данные из источника?

♦ Каков ожидаемый объем данных?

♦ В каком формате представлены данные? Может ли этот формат быть принят при

последующем хранении и преобразовании?

♦ Подходят ли исходные данные для немедленного использования потребителями

ниже по потоку? То есть качественные ли данные? Какая постобработка требу­

ется для их предоставления потребителю? Каковы риски, связанные с качеством

данных (например, может ли бот-трафик на сайте загрязнить данные)?

♦ Требуется ли обработка данных в полете для последующего поглощения ниже

по потоку выполнения, если данные поступают из потокового источника?

Эти вопросы относятся к пакетному и потоковому поглощению данных, а также

к базовой архитектуре, которую вы будете создавать, строить и поддерживать.

Независимо от частоты поступления данных, при проектировании архитектуры по­

глощения необходимо учитывать следующие факторы:

1. Ограниченность и неограниченность.

♦ Частота.

♦ Синхронность и асинхронность.

♦ Сериализация и десериализация.

♦ Пропускная способность и масштабируемость.

♦ Надежность и устойчивость.

♦ Полезная нагрузка.

♦ Модели Push, Pull и Poll.

Неограниченные данные - это данные в том виде, в каком они

существуют в реальности, как происходят события, спорадически или постоянно,

непрерывно и текуче. Ограниченные данные - это удобный способ группировки

данных по каким-либо границам, например по времени.

У систем на основе пакетной обработки часто довольно низкая производитель­

ность, когда пользователи пытаются выполнить множество мелких пакетных опе­

раций, а не меньшее количество крупных операций. Например, если в транзакци­

онных базах данных принято вставлять по одной строке за раз, то для многих баз

данных на основе столбцов эта схема не подходит, поскольку она вынуждает соз­

давать множество маленьких неоптимальных файлов и заставляет систему выпол­

нять большое количество операций создания объектов.

Приведем несколько предложений для смягчения влияния проблем, связанных

с эволюцией схем. Во-первых, если у вашего фреймворка обработки событий есть

реестр схем ( о нем говорилось ранее в этой главе), используйте его для создания

версий изменений схем. Далее, очередь недоставленных сообщений (описана в раз­

деле «Обработка ошибок и очереди недоставленных сообщений») может помочь

в исследовании проблем с не обработанными должным образом событиями.

Непоглощенные события необходимо пере­

направить и сохранить в отдельном месте, называемом очередью недоставленных

сообщений (Dead-Letter Queue, DLQ).

Очередь недоставленных сообщений отделяет проблемные события от событий,

которые могут быть приняты потребителем (рис. 7.12). Если события не перена­

правляются в эту очередь, то такие ошибочные события рискуют заблокировать

поглощение других сообщений. Инженеры данных могут использовать DLQ для

диагностики причин возникновения ошибок

JDBC и ODBC долгое время были золотыми стандартами для получения данных из

БД, но для многих приложений, связанных с инженерией данных, эти стандарты

подключения начинают терять свою актуальность. Эти стандарты подключений не

справляются с вложенными данными и передают данные в виде строк. Это означа­

ет, что нативные вложенные данные должны быть перекодированы в строковые для

передачи по сети, а столбцы из баз данных на основе столбцов должны быть по­

вторно сериализованы в виде строк.

CDC и репликация баз данных

СОС может использоваться для репликации между базами данных - события бу­

феризируются в поток и асинхронно записываются во вторую базу данных. Однако

многие базы данных изначально поддерживают версию репликации с сильной свя­

занностью ( синхронную репликацию), при которой реплика полностью синхрони­

зируется с основной базой данных. Синхронная репликация обычно требует, чтобы

первичная база данных и реплика были одного типа (например, из PostgreSQL

в PostgreSQL). Преимущество синхронной репликации заключается в том, что вто­

ричная база данных может разгрузить первичную, выступая в роли реплики для

считывания, - запросы на считывание могут быть перенаправлены на реплику.

Запрос вернет те же результаты, которые были бы получены из основной базы дан­

ных.

СОС не бесплатна. СОС потребляет различные ре­

сурсы базы данных, такие как память, пропускная способность диска, хранилище,

процессорное время и пропускная способность сети.
